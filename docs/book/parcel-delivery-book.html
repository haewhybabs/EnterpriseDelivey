Chapter 1

Why We Tore It Down and Started Over

Years ago, a Spring Boot project called EnterpriseParcelDelivery got built. It worked. It modeled a real business — users send parcels, drivers deliver them, recipients receive them, senders rate the experience. It used real design-pattern vocabulary: factories, services, repositories, DTOs. On paper, it looked like serious backend work.

Then years passed on mobile engineering, and the backend muscle went quiet. The plan to get it back wasn't to read about Spring Boot — it was to rebuild this exact project, from an empty folder, typing almost every line by hand, verifying every single claim against a real running database instead of trusting that code "probably works."

The honest audit of the old project

Before touching any code, the old project got a real review, not a nostalgic glance. A few things stood out:

  • The "Factory" classes weren't factories. In proper object-oriented design, a Factory decides which class to instantiate based on some condition. The old project's DeliveryRequestFactory, UserFactory, and friends did something much simpler: they copied fields from a DTO into an Entity, and from an Entity into a response DTO. That's a Mapper, not a Factory. Calling it the wrong name in an interview, when a sharp interviewer asks "so what varies at runtime here?", is exactly the kind of gap that costs credibility. This correction became the seed of a whole rebuilding philosophy: name things by what they actually do, not by what sounds impressive.
  • The tooling was years out of date. Spring Boot 2.7.6 (end of life), a JWT library (jjwt 0.9.1) with known vulnerabilities, and a Spring Security base class (WebSecurityConfigurerAdapter) that has since been deleted entirely from the framework.
  • The security was broken in a way that would fail any real review. The JWT signing secret was the literal string "password1", hardcoded directly in Java source and checked into version control. Tokens lived for 504 hours (21 days).
  • There were no transactions anywhere, despite several service methods writing across four or five separate database tables in sequence. If anything failed halfway, the data would be left in an inconsistent state.
  • Errors were conflated. "This doesn't exist" and "you sent me garbage" were both handled by the same exception type, returning the same HTTP 400 status — even though they mean genuinely different things to a client.
The core decision None of this made the old project worthless. It made it a blueprint: a complete, correct description of what the system needs to do (the tables, the relationships, the feature list), stripped of any temptation to copy-paste the actual implementation. The rebuild uses the blueprint, not the code.

How the reset actually happened

Git made this safe. The old code was never deleted — it was tagged onto a branch called legacy-reference, left exactly as it was, permanently available to glance back at. Then a brand new branch, rebuild-2026, was created as an orphan branch — meaning it starts with zero shared history with the old code, a genuinely empty slate, not a copy with the old files just sitting there unused.

Two kinds of "cleaning" happened on top of that. The first was mechanical housekeeping: deleting the Maven build output folder (target/, which regenerates every time you build and should never be tracked by git), and Mac-specific junk files (.DS_Store). The second, more important kind, was a mental discipline: treat the old project as a reference document to be read, never a file to be copied into the new one.

The four-languages temptation, and why it was rejected

The original plan was ambitious: rebuild this same project four separate times, in Spring Boot, Node.js, Go, and Django/FastAPI, to demonstrate broad backend fluency. A second opinion pushed back hard on this, and the pushback held up under scrutiny: four shallow rebuilds teach the same CRUD endpoints in four different syntaxes. By the third language, nothing new is being learned — just translation. A hiring manager looking at four similar-looking repositories sees "knows the basics everywhere," not "can run a production backend."

The revised plan: go genuinely deep on one stack (Spring Boot, since it matches prior experience and dominates UK/enterprise/fintech hiring), rebuild it to an actual 2026 production standard (proper transactions, real security, caching, tests, deployment), and only then introduce a second language as a deliberate architectural choice — splitting off one real microservice (originally planned as a notifications/tracking service in FastAPI) that talks to the Spring Boot core over a real contract, rather than existing as a parallel, disconnected rewrite.

Chapter 2

Laying the Foundation: Project Setup and Tooling

The kitchen analogy

Before any backend writes a single meaningful line of business logic, it needs four things, no more: a door that listens for incoming requests, a filing system that organizes data flowing in and out, a pantry where information is actually stored long-term, and a bouncer deciding who's allowed to ask for what. Everything else — every annotation, every library, every clever pattern — is detail layered on top of those four ideas.

Picking the toolchain, and getting surprised by it

The project was generated using Spring Initializr — the standard way nearly every real Spring Boot project begins, rather than hand-writing a build file from memory. The first real lesson arrived immediately and unplanned: querying Spring Initializr's live metadata revealed that Spring Boot 4.1.2 was the current stable release, not the 3.x line that older training material or memory would suggest. This mattered enough to call out explicitly: when the ecosystem moves faster than what's in your head, trust the live source of truth (the actual package registry, the actual compiler output) over what you remember.

Spring Boot 4 also quietly renamed some familiar starters — spring-boot-starter-web became spring-boot-starter-webmvc, and the old single spring-boot-starter-test split into feature-specific test starters. None of this was guessed; it was confirmed by letting Maven actually try to resolve the dependencies and reading the real error messages when a version string was wrong.

Two real debugging detours, both instructive

Detour One: the missing wrapper The Maven Wrapper (mvnw) is a script that auto-downloads the exact right build tool version, so nobody needs Maven installed globally. Its companion folder, .mvn/, starts with a dot — which makes it hidden on a Mac. Finder's double-click unzip silently dropped that hidden folder during extraction, leaving the wrapper script with no instructions to follow. The fix: re-fetch the project via the command line (curl + unzip), which doesn't have Finder's blind spot for dotfiles.
Detour Two: the version string typo Spring Initializr's own metadata listed the Spring Boot version with a legacy .RELEASE suffix (a naming convention the project dropped years ago in its actual published artifacts). Copying that string literally into pom.xml caused Maven to search for a version that doesn't exist on Maven Central. The fix was found by querying Maven Central's own metadata directly and comparing it to what had been typed — the real artifact version was simply 4.1.2, no suffix.

Java 21, and a small machine-setup wrinkle

The machine only had Java 17 installed. Java 21 was chosen deliberately for currency (it's the newer LTS release, and its headline feature, virtual threads, is a legitimate talking point in a backend interview about concurrency). It was installed via Homebrew, but deliberately not symlinked into the system Java location (which would have needed sudo). Instead, every Maven command runs with an explicit environment variable:

JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./mvnw spring-boot:run

This is a small but real lesson in itself: you don't always need administrator privileges to point a build tool at a specific tool version. An environment variable, scoped to just the one command, is often enough.

Chapter 3

The Pantry: Postgres and Docker

A backend with no database is a kitchen with an empty pantry — the lights can be on, the door can be open, but there's nothing to actually serve. This chapter is about standing up that pantry without permanently installing Postgres onto a personal machine.

Docker Compose, explained without jargon

Docker lets you describe "I want a Postgres database running in its own isolated little box" as a short text file, and have it simply appear — then vanish cleanly later, with zero leftover mess on the host machine. That text file is docker-compose.yml:

services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_DB: parcel_delivery
      POSTGRES_USER: parcel_app
      POSTGRES_PASSWORD: devpassword
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:

Reading it plainly: grab the official pre-built Postgres version 17 image rather than building one from scratch; create a database called parcel_delivery with a specific login; expose Postgres's internal port 5432 to the outside world so the app (running directly on the host, not inside Docker) can reach it; and keep the actual data files on a named, persistent volume so stopping the container doesn't throw away everything stored in it.

A real typo-hunt, worth retelling

The first attempt at this file had four separate mistakes, each instructive on its own:

MistakeWhy it mattered
postgress instead of postgres (image name)Docker Hub has no image with that name — the pull fails outright.
POSTGRESS_DB, _USER, _PASSWORD (extra S)The official image only recognizes the exact spelling POSTGRES_*. Misspelled variables are silently ignored, and with no password set at all, the container refuses to boot as a safety measure.
volume: instead of volumes:, wrongly indentedYAML is whitespace-sensitive. The wrong indentation nested this block inside services:, which Docker Compose interpreted as "there's a service literally called volume" — a structurally different, invalid document.
Mismatched volume name (pdgata vs. pgdata)The mount reference and the declared volume name must be the identical string, or Docker treats them as two unrelated things.

Every one of these is the kind of mistake that's easy to make and, critically, easy to debug once you know what Docker's actual error message is trying to tell you. None of them were fixed by guessing — each fix came from reading the specific error Docker Compose printed and tracing it back to the exact line responsible.

Connecting the app to the pantry

Once the container was confirmed healthy (via docker ps and pg_isready, not just "it looks like it started"), three lines in application.properties told the Spring Boot app where to find it:

spring.datasource.url=jdbc:postgresql://localhost:5432/parcel_delivery
spring.datasource.username=parcel_app
spring.datasource.password=devpassword

These three values have to match the container's POSTGRES_* settings exactly — a mismatch here produces a login rejection, not a "can't find it" error, which is a useful distinction when something doesn't connect.

A deliberate shortcut, named honestly For most of this build, Hibernate was allowed to auto-create and adjust tables itself (spring.jpa.hibernate.ddl-auto=update), with the generated SQL printed to the console (spring.jpa.show-sql=true) so every table could be inspected the moment it was created. This is explicitly a learning-phase convenience, not a production pattern — real systems version their schema changes with migration tools like Flyway (which the old project actually used, and which this rebuild plans to reintroduce once the entity shapes fully settle).
Chapter 4

Modeling the World: Entities and Relationships

An Entity is just a regular Java class with a handful of special annotations that tell Hibernate "this class is a database table — when you save an object of this class, turn it into a row." Eight entities make up the whole system, and building them in a deliberate order — simplest first — meant every new relationship concept landed on top of a solid, already-understood foundation.

The cast of characters

  • Role — the simplest table: an id, a unique name ("Sender", "Driver", "Admin"), timestamps. No relationships at all.
  • User — a name, email, hashed password, and a Role. The first entity with a real relationship.
  • Driver — an optional extra profile a User can have: phone number, address. The first one-to-one relationship.
  • Parcel — belongs to a User, has a name and description.
  • RecipientAddress — also belongs to a User: an address, a recipient's phone and email.
  • DeliveryStatus — a lookup table, just like Role: "Awaiting delivery", "Processing", "In transit", "Delivered".
  • DeliveryRequest — the hub of the whole system: it ties together a User, a Parcel, a RecipientAddress, a DeliveryStatus, and (eventually, optionally) a Driver, plus a sender address and a delivery date.
  • Rating — one-to-one with a DeliveryRequest: a single integer score.

Relationships, explained without the jargon first

Underneath, a relationship between two tables is just one table having a column that holds another table's ID — a foreign key. JPA's annotations are a way of writing that pointer as a normal Java field (private Role role;) instead of manually writing SQL joins everywhere.

  • Many-to-one — many rows point at one row. Many Users can share one Role.
  • One-to-many — the same relationship, viewed from the other side. One Role has many Users.
  • One-to-one — exactly one row matches exactly one row. One User has at most one Driver profile.
  • Many-to-many — rows on both sides can match several on the other. This system doesn't actually have one of these — a sign the data model is simpler than it could have been, which is a good thing.

Who "owns" the relationship

In a real database, the actual foreign key column has to physically live on one side only. Since delivery_request.user_id exists as a column on the delivery_request table (not the other way around), DeliveryRequest is the owning side — it holds the real pointer, declared with @JoinColumn. User would be the inverse side if it ever needed to look back ("give me all the delivery requests for this user") — but that reverse-lookup field was deliberately never added, because nothing in the system actually needed it yet. Adding relationships "just in case" is exactly how real codebases end up slow and tangled.

Lazy loading and the N+1 problem

Every relationship in this project uses fetch = FetchType.LAZY, deliberately, instead of the JPA default of eager loading. Eager loading means: load a User, and Hibernate automatically also loads their Role in the same breath, whether you asked for it or not. That sounds convenient, but it becomes a real performance trap once an entity has several relationships — loading one DeliveryRequest could silently drag in its User, Parcel, Driver, DeliveryStatus, and RecipientAddress, each as a separate database round-trip. This is called the N+1 problem: one query to get the list, N additional queries fired off one row at a time instead of one efficient combined query. It's one of the most commonly asked backend interview questions, and this project deliberately sets itself up to deal with it properly later (via explicit joins or targeted projections) rather than stumbling into it by accident.

Three real design decisions, made deliberately

Decision: Driver → User cascade delete If a User is deleted, should their Driver profile vanish automatically? Yes — a driver profile has no meaning without the user it belongs to. This is expressed with a Hibernate-specific annotation, @OnDelete(action = OnDeleteAction.CASCADE), which bakes ON DELETE CASCADE directly into the real database constraint. This matters because JPA's own cascade attribute only works when a delete happens through Hibernate — it does nothing if a row is removed by a raw SQL script or an admin tool. The database-level annotation guarantees the rule holds no matter how the delete happens.
Decision: Parcel → User, no cascade The opposite call, for a good reason: if a user is deleted, their parcels should not vanish — they may carry historical or audit value. The foreign key is left at its default behavior, RESTRICT, meaning Postgres will simply refuse to delete a user who still has parcels on record, forcing a deliberate decision rather than a silent data loss.
Decision: DeliveryRequest → Parcel, many-to-one on purpose A direct question was asked during the build: "why isn't this a one-to-one? Can't the same parcel end up in two delivery requests?" The honest answer: it depends on a business rule that the old project never actually decided. The choice made here was deliberate — re-delivery attempts are a supported feature. If a delivery fails and a parcel is returned to the sender, a brand new DeliveryRequest row can be created for that same parcel, tracking a fresh attempt. If that business rule ever changes, the fix is one line: adding unique = true to the join column.
Chapter 5

Cutting the Boilerplate: Lombok

Every entity, up to this point, had been written with getters and setters typed out by hand — deliberately, on purpose, to feel the real cost of it before automating it away. By the time the sixth field appeared on the busiest entity in the system, the boilerplate pain was undeniable, and that was exactly the right moment to bring in Lombok.

What Lombok actually does

Lombok is a compile-time tool. It reads annotations like @Getter and @Setter on a class and generates the equivalent methods before the real Java compiler even sees them. Nothing magical happens at runtime — the final compiled class is indistinguishable from one written by hand. It's a shortcut in how the source is written, not a change in how the program behaves.

The dangerous shortcut that was deliberately avoided

Never use @Data on an entity Lombok's @Data annotation generates getters, setters, and equals()/hashCode()/toString() all at once. On a JPA entity, this is a well-known, genuinely dangerous combination. Generated equals()/hashCode() would touch lazy-loaded relationships, silently triggering extra database queries just from putting an entity into a HashSet. Worse: an entity's id is null before it's saved and becomes a real number after — if hashCode() includes id, the object's hash code changes after saving, which breaks the fundamental rule that an object's hash code must stay stable while it sits in a hash-based collection. This project uses only @Getter and @Setter on entities, deliberately, everywhere.

The payoff was immediate and visible: the Rating entity, built with Lombok from the start, ended up roughly twenty lines shorter than an equivalent hand-written version — and because the pain of writing it by hand had already been felt once, the shortcut meant something instead of being invisible magic copied from a tutorial.

Chapter 6

Repositories: Talking to the Database Without Writing SQL

A Repository in Spring Data JPA is an interface with no implementation written anywhere. Declare extends JpaRepository<Role, Long>, and Spring automatically builds a real, working implementation behind the scenes at startup — save(), findById(), findAll(), delete(), all for free.

Query derivation: the genuinely clever part

Declare a method like findByEmail(String email), and Spring reads the method name itself and builds the SQL query from it — WHERE email = ? — with no annotation, no SQL, no implementation written. It understands relationships too: findByUserId(Long userId) on DeliveryRequest correctly produces WHERE user_id = ?, even though the actual field is called user (a User object, not a raw ID) — Spring walks into the relationship and finds user.id automatically.

This isn't guesswork at startup, either — Spring Data JPA actually validates every derived method name against the entity's real properties the moment the application boots. A typo in a method name doesn't fail quietly; it fails loudly and immediately, with a clear error, before a single request is ever served.

A deliberate, principled choice: Optional everywhere

Every single-result lookup across all eight repositories returns Optional<T>, never the entity directly. This is the direct, structural fix for the old project's worst habit — .orElse(null) scattered through its services, silently turning "nothing found" into a null that could slip through and crash something unrelated much later. Optional forces whoever calls the method to explicitly decide what happens when nothing is found, right there, instead of deferring that decision into a landmine.

Chapter 7

DTOs and Mappers: Never Hand Over the Database Directly

An Entity is a database-shaped object — it exists to describe a table. A DTO (Data Transfer Object) is a deliberately separate, simple class that describes what actually travels over HTTP, in a request or a response. They can look similar for a simple entity like Role, but the separation earns its keep the moment a more sensitive entity like User enters the picture.

Three concrete reasons this isn't decoration

  1. Security. User's entity has a password field (holding a BCrypt hash, covered properly in the security chapter). If a controller ever accidentally returned the User entity directly, that hash would land straight in a JSON response, visible to anyone. A DTO that was never given a password field physically cannot leak one.
  2. Stability. Adding an internal field to an entity later — an audit flag, an internal note — would otherwise silently become part of the public API the moment it's added, whether that was intended or not. A DTO is a contract deliberately controlled by the author, not an accident of whatever the database happens to contain.
  3. Avoiding real crashes. Returning an entity with lazy-loaded relationships directly as JSON can throw a serialization error, because the library converting the object to JSON tries to read a relationship that was never actually loaded from the database in the first place.

The Mapper: the corrected "Factory"

This is the direct payoff of the correction made in Chapter 1. A Mapper is a small, dedicated class whose only job is converting between an Entity and its DTOs — exactly what the old project's misleadingly-named "Factory" classes actually did. Naming it correctly this time isn't pedantry; it's the difference between describing a pattern accurately under interview pressure and getting caught overstating it.

@Component
public class RoleMapper {
    public RoleResponseDTO toResponseDTO(Role role) {
        RoleResponseDTO dto = new RoleResponseDTO();
        dto.setId(role.getId());
        dto.setName(role.getName());
        return dto;
    }
}

@Component here, rather than @Service or @Repository, is the generic Spring annotation meaning "let the framework manage this object, it doesn't fit a more specific category." It's worth knowing that @Service, @Repository, and @Controller are all actually built on top of @Component under the hood — just more specific labels for the same underlying mechanism.

Chapter 8

Services, Controllers, and Getting Errors Right

Constructor injection over field injection

The old project wired its dependencies like this:

@Autowired
private RoleRepository roleRepository;

This is field injection — Spring reaches directly into a private field via reflection and sets it after the object already exists. For a brief moment, the object technically exists in a half-built state, and more importantly, it's awkward to hand the object a fake dependency in a unit test without spinning up Spring's entire container.

This rebuild uses constructor injection throughout instead, with Lombok's @RequiredArgsConstructor doing the typing:

@Service
@RequiredArgsConstructor
public class RoleService {
    private final RoleRepository roleRepository;
    private final RoleMapper roleMapper;
    ...
}

@RequiredArgsConstructor looks at every final field and generates a constructor taking exactly those as parameters. Spring sees a class with exactly one constructor and automatically uses it — no @Autowired needed anywhere. final also means the field can only be set once, at construction, which makes it structurally impossible for a service to exist with a missing dependency.

A mistake that recurred three times This single detail — forgetting the final keyword — caused the exact same class of bug three separate times during this build (first in DeliveryRequestController, then again in AuthController). Without final, Lombok generates an empty constructor instead (there's nothing to include), Spring has nothing to inject into, and the field stays null forever — guaranteeing a crash the instant the endpoint is actually called. It compiles perfectly cleanly. The bug only shows up at runtime, and only on the exact code path that uses the broken field. This is worth remembering precisely because it recurred: it's a specific, nameable mental-model gap, not a random typo, and naming it clearly is what finally made it stop happening.

Getting HTTP status codes right: a four-way taxonomy

The old project threw one generic exception type for every error condition, which meant "this doesn't exist" and "you sent me garbage" both came back as the same HTTP 400. This rebuild settled on four distinct categories, added one at a time, exactly when a real situation demanded each one:

ExceptionStatusMeaningExample
ResourceNotFoundException404A specific thing the caller referenced by ID should exist, and doesn't.Looking up a role by an ID that was deleted.
BadRequestException400The caller's input itself is invalid.Registering with an email that's already taken; an invalid role name.
AuthenticationException (Spring Security's own type)401The caller isn't who they claim to be.Wrong password at login.
Unmapped RuntimeException / IllegalStateException500The system's own setup is broken — not the caller's fault.The default "Awaiting delivery" status row is missing from the database.

That last row deserves its own explanation, because it's a genuinely subtle distinction. When a new DeliveryRequest is created, it needs a default status — something the system itself is supposed to have seeded, not something the client provides. If that lookup ever came back empty, it would mean the system's own data is broken, which is neither the client's fault (not 400) nor quite the same flavor of "missing resource" as a normal 404. A plain IllegalStateException, deliberately not caught by the custom exception handler, falls through to Spring's own generic 500 — the client gets a safe, generic error with no internal details leaked, while the real cause ("Default delivery status 'Awaiting delivery' is not seeded in the database") remains fully visible in the server's own logs, down to the exact file and line number.

One more deliberate choice, tied to the 401 case: the error message for a failed login is always the same generic text — "Invalid email or password" — regardless of whether the email didn't exist or the password was simply wrong. Returning a different message for each case would let an attacker discover which email addresses are actually registered, one guess at a time. Same message, every time, regardless of which half was actually wrong.

All of this, wired together

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<Map<String, String>> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(Map.of("message", ex.getMessage()));
    }

    @ExceptionHandler(BadRequestException.class)
    public ResponseEntity<Map<String, String>> handleBadRequest(BadRequestException ex) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(Map.of("message", ex.getMessage()));
    }

    @ExceptionHandler(AuthenticationException.class)
    public ResponseEntity<Map<String, String>> handleAuthException(AuthenticationException ex) {
        return ResponseEntity.status(HttpStatus.UNAUTHORIZED).body(Map.of("message", "Invalid email or password"));
    }
}

@RestControllerAdvice is a single class that catches exceptions thrown anywhere across every controller in the entire application — one place, instead of a repeated try/catch in every endpoint. This idea existed in the old project too (as ApplicationExceptionHandler); what changed is the discipline around which status code actually means what.

Chapter 9

The Core Business Flow, End to End

With entities, repositories, DTOs, mappers, services, and controllers all in place, the actual story the system tells came together as a sequence of real, working endpoints — each one verified not by reading the code and nodding, but by running it, calling it with real HTTP requests, and checking the actual rows that landed in Postgres afterward.

The flow, step by step

  1. Register. POST /api/users/register — takes a name, email, password, and a role name. The password is hashed with BCrypt before it ever touches the database (full detail in Chapter 10). Registering with an email already in use, or a role name that doesn't exist, both correctly return 400.
  2. Become a driver. POST /api/drivers/create — a user opts into a driver profile. Trying to do this twice for the same user correctly returns 400 ("already registered as a driver"); the duplicate check happens explicitly, before the database's own unique constraint would have caught it anyway, purely to produce a clean error message instead of a raw database exception leaking through.
  3. Create a parcel. POST /api/parcels — a sender describes something they want delivered.
  4. Add a recipient address. POST /api/recipient-addresses — where the parcel is actually going, and who's receiving it.
  5. Submit a delivery request. POST /api/delivery-requests/create — the hub action, tying a user, a parcel, and a recipient address together, with a status that defaults automatically to "Awaiting delivery" and no driver assigned yet.
  6. Assign a driver. PATCH /api/delivery-requests/{id}/assign-driver — the first use of PATCH in the project: mutating one field of something that already exists, rather than creating something new.
  7. Update delivery status. PATCH /api/delivery-requests/{id}/status — moving a request through "Processing", "In transit", "Delivered". An invalid status name returns 400, reusing the exact same reasoning as an invalid role name at registration.
  8. Rate the delivery. POST /api/ratings — restricted, by a deliberate business decision, to only requests whose status is already "Delivered". Attempting to rate anything earlier in the lifecycle correctly returns 400; attempting to rate the same delivery request twice also correctly returns 400, for the same "defend against the obvious before the database has to" reasoning as the duplicate-driver check.
A real debugging story worth retelling While building the delivery-request submission endpoint independently, a genuinely subtle bug surfaced: DeliveryRequestMapper called deliveryRequest.getDriver().getId() unconditionally. Right after creation, getDriver() returns null — that's not an edge case, it's the normal state, since no driver has been assigned yet. Calling .getId() on null crashes immediately. The fix connects directly back to Chapter 4's lesson about optional relationships: nullable in the entity means every piece of code touching it must null-check, with no exceptions. deliveryRequest.getDriver() != null ? deliveryRequest.getDriver().getId() : null fixed it, and the underlying lesson — that a design decision made early (making a field nullable) has real consequences for code written much later — is the kind of thing that only really sticks after it causes an actual bug.

Every single step above was tested the same way, deliberately, every time: boot the real app, hit the real endpoint with curl, read the actual HTTP response, and then query Postgres directly to confirm the row that landed matches what was expected — never trusting a green checkmark without seeing the underlying data.

Chapter 10 — A Chapter of Its Own

JWT Authentication

This is the chapter that closes the single biggest security gap in the old project. The old JWT secret was the literal string "password1", hardcoded in source and committed to version control. Rebuilding this properly, piece by piece, is the centerpiece of the whole security story.

What a JWT actually is — and isn't

A JSON Web Token is not encrypted. It's three chunks of base64-encoded text glued together with dots: header.payload.signature. Anyone can decode the middle part and read its contents in plain text — there's an entire public website (jwt.io) built around doing exactly that. What the signature buys is tamper-proofing, not secrecy: change a single character of the payload, and the signature no longer matches, so the server rejects it outright. The practical rule that falls out of this: never put anything genuinely secret (a real password, a card number) inside a JWT's contents — only things that are safe to be read by anyone holding the token, like an email address or a user ID.

Password hashing: BCrypt, and why it's deliberately slow

A password is never stored as typed — not even in a form the system's own operators could read back. It's run through a one-way function that turns "mypassword123" into something like $2a$10$N9qo8uLOickgx2ZMRZoMy..., with no way to reverse it. At login, the freshly typed password is hashed again and the two hashes are compared — the original is never "decrypted," because it can't be.

BCrypt specifically is chosen because it's deliberately slow — it performs thousands of internal rounds of work by design. That sounds like a downside, but it's the entire point: a fast hash lets an attacker who steals a database try billions of password guesses per second; BCrypt limits that to a few hundred. Exposing the actual hashing mechanism as a Spring bean, rather than constructing it directly inside a service, follows the same "depend on the interface, not the implementation" principle used throughout this project:

@Configuration
public class PasswordConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

Generating and checking tokens: JwtUtil

A modern JWT library (jjwt 0.12.6) replaced the old project's jjwt 0.9.1 — and the API itself genuinely changed in that time, confirmed not by memory but by letting the real compiler validate the new fluent syntax:

public String generateToken(String email) {
    Date now = new Date();
    Date expiry = new Date(now.getTime() + expirationMs);
    return Jwts.builder()
            .subject(email)
            .issuedAt(now)
            .expiration(expiry)
            .signWith(getSigningKey())
            .compact();
}

The secret itself is read from an environment variable, with a clearly-labeled local-only fallback for convenience — jwt.secret=${JWT_SECRET:this-is-only-a-local-dev-secret-change-it-before-any-real-deploy} — the direct structural fix for the old hardcoded string. It's worth noting that HS256 signing has a genuine minimum key length (256 bits / 32 bytes); the old secret, at nine characters, was not just bad practice but too short to be cryptographically sound even if it had been kept private.

Telling Spring Security how to find a user

UserDetailsService is a one-method contract: given an identifier, return the username, password hash, and roles. The method is confusingly named loadUserByUsername even though this project passes it an email — that's just historical naming baked into the interface itself.

public UserDetails loadUserByUsername(String email) {
    User user = userRepository.findByEmail(email)
            .orElseThrow(() -> new UsernameNotFoundException("No user found with email: " + email));

    return new org.springframework.security.core.userdetails.User(
            user.getEmail(),
            user.getPassword(),
            List.of(new SimpleGrantedAuthority("ROLE_" + user.getRole().getName().toUpperCase())));
}

UsernameNotFoundException is deliberately not the project's own custom exception — Spring Security watches for this specific type internally, and turns it into a generic authentication failure, preventing "that email doesn't exist" from ever being distinguishable from "wrong password" to an outside observer. The prefix "ROLE_" on the authority string is a Spring Security convention: a later check like hasRole("ADMIN") is secretly checking for an authority literally spelled "ROLE_ADMIN" — forgetting the prefix is a classic, quietly-broken bug.

Checking the token on every request: JwtAuthFilter

This is a filter, not a controller — and that distinction matters enormously. Filters run before Spring routes a request to any controller, which means the custom @RestControllerAdvice error handler from Chapter 8 never sees anything thrown from inside one. A bad or expired token has to be handled locally, right there, by simply treating the request as unauthenticated rather than letting an exception escape into an ugly default error page:

try {
    String email = jwtUtil.extractEmail(token);
    if (email != null && SecurityContextHolder.getContext().getAuthentication() == null) {
        UserDetails userDetails = userDetailsService.loadUserByUsername(email);
        if (jwtUtil.isTokenValid(token, email)) {
            UsernamePasswordAuthenticationToken authToken =
                    new UsernamePasswordAuthenticationToken(userDetails, null, userDetails.getAuthorities());
            authToken.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
            SecurityContextHolder.getContext().setAuthentication(authToken);
        }
    }
} catch (Exception e) {
    // Malformed, expired, or tampered token - leave the request unauthenticated.
}

SecurityContextHolder is best understood as "who is authenticated, for this one request, on this one thread" — once set here, every later piece of code handling this same request can ask who's logged in.

The config that wires it all together: SecurityConfig

The old project's WebSecurityConfigurerAdapter base class has been removed entirely from current Spring Security — this isn't a style preference, the old code genuinely would not compile against a current version. The replacement is a @Bean method returning a built SecurityFilterChain:

@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.disable())
        .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**", "/api/users/register").permitAll()
            .anyRequest().authenticated())
        .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
    return http.build();
}

CSRF protection exists to stop a malicious website from tricking a browser into reusing an existing session cookie. This system never uses cookies — the token travels explicitly in an Authorization header on every request, which a malicious site has no way to silently attach — so disabling CSRF here is the architecturally correct choice, not a shortcut. SessionCreationPolicy.STATELESS tells Spring Security to never create or rely on a server-side session at all: every request proves who it is from scratch, which is the actual reason JWTs scale well across multiple servers with no shared state to coordinate.

The login endpoint

public AuthResponseDTO login(AuthRequestDTO dto) {
    authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(dto.getEmail(), dto.getPassword()));

    User user = userRepository.findByEmail(dto.getEmail())
            .orElseThrow(() -> new ResourceNotFoundException("User not found with email: " + dto.getEmail()));

    AuthResponseDTO response = new AuthResponseDTO();
    response.setToken(jwtUtil.generateToken(user.getEmail()));
    response.setEmail(user.getEmail());
    response.setRoleName(user.getRole().getName());
    return response;
}

The one line doing all the real work is authenticationManager.authenticate(...) — it uses CustomUserDetailsService to look the user up, then PasswordEncoder to check the submitted password against the stored BCrypt hash, throwing the Chapter 8 AuthenticationException if either step fails. The application's own code never compares a password itself, anywhere.

The hardest bug of the entire project

Case study: the LazyInitializationException

Everything above compiled cleanly, booted cleanly, and still failed in a way that wasn't obvious from reading the code: a genuinely valid JWT, presented to a protected endpoint, still came back 403 — identical to having no token at all. The filter was clearly running (confirmed via Spring Security's own debug logging), but something inside it was silently failing, swallowed by an empty catch block that had no logging at all.

Temporarily printing the real stack trace revealed the true cause:

org.hibernate.LazyInitializationException:
Could not initialize proxy [Role#1] - no session

The exact line: user.getRole().getName(), inside CustomUserDetailsService.

Here's the genuinely non-obvious part. Back in Chapter 4, Spring Boot had warned, at every single boot, about spring.jpa.open-in-view being enabled by default — a setting that keeps a database session open for the duration of a request so that lazy relationships can still be read later, without needing to plan every query upfront. The natural assumption is that this covers the entire HTTP request. It doesn't. open-in-view's session is scoped specifically around Spring MVC's handling of a request — and Spring Security's filters, including the custom JwtAuthFilter, run before MVC even starts. By the time the filter tried to read user.getRole(), no database session existed yet for this request at all.

The fix is small, and it's the first genuine use of @Transactional anywhere in this entire rebuild — a gap flagged as missing all the way back when the old project's multi-table write methods were first reviewed in Chapter 1:

@Override
@Transactional(readOnly = true)
public UserDetails loadUserByUsername(String email) { ... }

@Transactional opens its own session for exactly as long as the method needs it, independent of where in the request pipeline the method is actually called from. This single bug taught something that no amount of reading about Spring Security would have made as memorable: open-in-view and Spring Security's filter chain operate in two different windows of time, and code that assumes otherwise will eventually break in exactly this way.

The real payoff: removing trust in the client entirely

With authentication genuinely working, the last and most important step was going back through every endpoint that had been quietly trusting a client-supplied userId in its request body — Parcel, RecipientAddress, Driver, and DeliveryRequest creation — and removing that field entirely. A small helper reads the real, token-verified identity directly:

@Component
@RequiredArgsConstructor
public class CurrentUserProvider {
    private final UserRepository userRepository;

    public User getCurrentUser() {
        String email = SecurityContextHolder.getContext().getAuthentication().getName();
        return userRepository.findByEmail(email)
                .orElseThrow(() -> new ResourceNotFoundException("Authenticated user not found: " + email));
    }
}

No controller needed to change at all — SecurityContextHolder is readable from inside a service directly, since it's scoped to the whole request thread, not just to controllers. Verified with a completely fresh second user: registered, logged in, and created a parcel, a recipient address, a driver profile, and a delivery request with no userId anywhere in any request body — and every single row that landed in Postgres correctly carried that user's real, token-derived ID. It is now structurally impossible for a client to create something "as" a different user by tampering with a request body, because there's no field left to tamper with.

Chapter 11

The Bugs That Taught the Most

A rebuild like this produces two kinds of value: the working code, and the specific mistakes caught along the way. The second kind is often more durable — a bug you've personally hit and diagnosed sticks in a way that reading about it never quite does. This chapter collects the ones worth remembering on purpose.

Chapter 12

What's Left: The Road to Production

Everything up to this point forms a genuinely complete core: a full relational data model, a full business flow, and real authentication with zero trust placed in anything a client claims about its own identity. What's left is the layer that separates "a working backend" from "something you'd actually trust running in production."

  • Transactions. @Transactional has been used exactly once so far (the security fix in Chapter 10). Several service methods still write across multiple repositories without an explicit transaction boundary — the original concern raised about the old project in Chapter 1, not yet fully resolved.
  • Caching. Redis, for data that's read far more often than it changes.
  • Events. Kafka or RabbitMQ, so a delivery status change can notify other parts of the system (or, eventually, a separate notifications service) without that service needing to be called synchronously and directly.
  • Testing. Unit tests, plus integration tests against a real database using Testcontainers — verifying with a script run by hand, as this entire project has done, doesn't scale, and doesn't protect against regressions.
  • Flyway migrations. Replacing the convenient-but-temporary ddl-auto=update and the manual SQL seeding used throughout this build with proper, versioned migration files — which is what the old project actually did correctly, and what this rebuild intends to bring back once the schema has fully settled.
  • CI/CD and a real deployment. A pipeline that runs tests automatically, and an actual small deployment somewhere real, rather than only ever running on one developer's machine.
  • Observability. Structured logs, metrics, and tracing — the tools that let someone understand what a running system is actually doing, rather than only what it's supposed to do.
  • The polyglot split, done properly. One deliberate service — originally planned as notifications or delivery tracking — carved out into a second language, talking to this Spring Boot core over a real contract. Not four parallel rewrites of the same CRUD app, which was the plan explicitly rejected back in Chapter 1.

The honest assessment, given mid-project: a 6 out of 10 at this point — strong on data modeling, dependency injection, and error-handling correctness, with no security, validation, transactions, tests, or deployment pipeline yet. Projected to a 9 out of 10 once this remaining list is actually built — not a 10, because no single project, however complete, teaches distributed-systems depth at real scale, or the texture of running something under genuine production load for months. That comes from the job itself, not from any solo rebuild. Which was, in the end, always the honest point of doing this at all.

Appendix

Glossary of Terms

Entity
A Java class annotated so Hibernate treats it as a database table — one object per row.
DTO (Data Transfer Object)
A plain class describing what travels over HTTP, deliberately separate from the entity it's related to.
Mapper
A small class converting between an Entity and its DTOs. What the old project mistakenly called a "Factory."
Repository
An interface, with no implementation written by hand, that Spring Data JPA fulfills automatically for talking to the database.
Service
A class holding business logic — the rules of what's allowed to happen, independent of both HTTP and raw data access.
Controller
A class mapping specific HTTP verbs and URL paths to specific methods, turning requests into calls on a service.
Constructor injection
Supplying a class's dependencies through its constructor (ideally auto-generated by Lombok's @RequiredArgsConstructor over final fields), rather than having Spring reach into private fields after the fact.
Lazy loading / FetchType.LAZY
A relationship is only actually fetched from the database when it's explicitly asked for, rather than automatically, every time the owning object is loaded.
N+1 problem
Loading a list of N items, then unintentionally firing one additional query per item to fetch each one's related data — N+1 total queries where one well-written query would have done.
Cascade delete
A database rule stating that deleting one row should automatically delete related rows, rather than leaving orphaned data behind.
JWT (JSON Web Token)
A signed, non-encrypted token proving who a request claims to be, without the server needing to remember anything between requests.
BCrypt
A deliberately slow, one-way hashing algorithm used to store passwords safely — the original can never be recovered from the stored hash.
Filter (Servlet Filter)
Code that runs on every incoming request before it's routed to any controller — where JWT validation happens, outside the reach of controller-level error handling.
SecurityContextHolder
Spring Security's way of tracking "who is authenticated, right now, for this one request."
@Transactional
Marks a method as needing its own database session/transaction boundary for its entire duration — independent of whatever else may or may not have a session open around it.
LazyInitializationException
Thrown when code tries to read a lazily-loaded relationship after the database session that could have fetched it has already closed.
CSRF (Cross-Site Request Forgery)
An attack where a malicious site tricks a browser into reusing an existing session cookie. Irrelevant to a stateless, header-based JWT API, which is why it's safely disabled here.
Idempotency
The property that doing something twice has the same effect as doing it once — not yet implemented in this project, but a known item on the production-hardening list.
